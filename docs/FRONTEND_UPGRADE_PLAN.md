# ipPping 前端轻量化升级计划

日期：2026-09-22。状态：待批准实施的计划；本次不修改生产代码、不部署。

执行状态补充：P0 的 P1 必需基线已建立，P1 已获准实施并于 2026-09-22 发布。交付与验证边界见 [P0/P1 实施记录](FRONTEND_P0_P1_REPORT.md)。完整跨设备基线及后续阶段不据此自动视为完成。

基线：仓库 `0b33aa6d72cff615433c7312b7116b5b0d6c1f63`，以及当日线上只读审阅。实施开始前必须复核基线是否变化。

## 1. 目标与结论

目标不是更换技术栈，而是在保留当前全部有效功能和视觉辨识度的前提下，同时降低主控计算、网络传输、浏览器渲染与维护成本，并使数据状态可信、发布可回滚。

推荐路线：**数据正确性与请求治理 → 组件和样式收敛 → 结构化数据契约 → Canvas 小范围验证 → 按需渲染 → 分阶段上线**。

- 保留原生 HTML/CSS/JavaScript，不以引入 React/Next.js 等框架作为现代化指标。
- 保留 SmokePing 采样和 RRD 存储；不需要依附原版 Web 页面，也不必继续以 PNG 作为唯一图表来源。
- 当前 PNG 已经由本项目 API 调用 RRDtool 生成，不是直接嵌入原版 Web。重绘收益应与这条实际链路比较。
- 优先试验轻量 Canvas 时间序列方案，uPlot 为首选验证候选，不预先承诺其一定优于现状。PNG 保留为兼容与导出通道。
- 先解决“未知变成正常、旧数据像实时数据、失败引发请求放大”，再调整装饰、字体或包体。
- 所有性能改善必须给出同场景前后对比；不承诺未经验证的节省百分比或全设备 120 FPS。

### 1.1 范围及非目标

本次范围：`web/`、相关数据 API、前端测试与构建发布方式、项目文档。后端改动仅服务于正确的数据契约和有界资源使用。

不在范围：节点增删、SSH 凭据、探针协议、节点容器、采样频率、每次 ping 数、RRD 保留策略、上传认证、重新开放原版 Web、扩大主控并发。既有安全和轻量化措施必须保留。

不默认新增：浅色主题、Inspector 详情侧栏、搜索系统、告警系统、抖动指标、后台自动刷新、外部遥测服务。它们不应混入性能重构而扩大需求。

### 1.2 历史文档如何处理

已核对主控上的历史 `PLAN.md`、`REDESIGN_PLAN.md` 及仓库的架构、轻量化文档。历史重设计稿包含尚未实施或与现网不同的愿景，例如默认浅色、表格加 Inspector、状态优先排序。

本次以“当前线上有效行为＋用户最新要求”为兼容基线：继续深色、Results/Charts、现有节点选择与字母排序，不借性能升级悄然替换产品。历史稿中缺失值不补零、按需绘制、字号可读、无持续动画等原则继续采用；冲突项记录为可选后续需求。Canvas 轴文字若由候选库绘制，应保证尺寸、对比度，并提供等价 DOM 摘要及数据入口，不机械套用历史稿“所有文字必须 DOM”而强行自研坐标系统。

## 2. 证据与不确定性

### 2.1 已确认的事实

| 编号 | 证据 | 对计划的直接影响 |
| --- | --- | --- |
| E01 | 本次审阅时 `server.py`、`web/app.js`、`web/styles.css`、`web/index.html` 的本地与生产内容校验一致；公开 JS/CSS 与源站一致 | 可以基于当前代码提出计划；实施前仍需重新比对 |

| E04 | 现有 `/api/series` 已能读取 RRD，但主前端尚未使用；没有显式最大点数参数 | 不必替换采样系统；先修契约和输出边界，再接 Canvas |

| E06 | 卡片查找逐项扫描 DOM；`showStat` 等路径存在写 DOM 后读取 `offsetWidth` | 用稳定 key 映射和集中布局处理，避免卡片增多后重复扫描和强制布局 |
| E07 | 图像队列并发 4，有懒加载，但首次主动排队 8 张；所有结果卡片 DOM 仍创建，离屏图片未统一释放 | “请求懒加载”尚不等于 DOM、像素内存和缓存有界 |
| E08 | series 的 `last_update` 来自最后时间桶；无有效数据时 summary loss 可为 0；当前值取范围内最后有效中位数 | 当前字段不能直接作为“最新采样/健康”依据，需要单独定义时效与缺失语义 |
| E09 | 前端当前值可回退到平均值；缓存存在性不等于未过期；页面没有数据自动刷新，仅有时钟定时更新 | 明确显示历史值、过期与未知；不能用绿色呼吸灯表示持续收到采样 |
| E10 | JS/CSS 仍使用旧固定版本查询串；公开 CDN 响应曾含 `max-age=14400,must-revalidate` | 必须引入内容指纹与 HTML 重验证，避免部署后客户端数小时看不到更新 |
| E11 | 移动端实测部分重要次级数值为 15 px、前景 `#666`、背景 `#1c1c1c`，对比度约 2.97:1 | 对正常尺寸的重要文本不足，应修复而不靠增大字号掩盖 |
| E12 | 桌面图像实际约 1944×750，显示约 1093×383；缩至移动宽度后仍使用旧大图，手动重新查询才改善刻度 | 尺寸响应应由容器驱动；Canvas 的局部重绘可避免此类重新取图 |
| E13 | 协议按钮缺少状态语义；Fix 按钮与父级键盘选择逻辑可能冲突；关闭移动抽屉后焦点可留在不可见控件 | 无障碍与交互状态应作为重构验收，不只是截图检查 |

关键代码定位以该基线为准：`web/app.js` 的并发定义约 38/78 行，批量刷新约 752 行，查找卡片约 1044–1054 行，卡片装载约 1185 行，数值显示约 1312 行；`server.py` 的序列读取约 219–308 行。实施后行号会变化，应以函数和测试定位。

### 2.3 尚不能下结论的部分

- 没有可靠的真实用户 LCP/INP/CLS 分位数据，不能宣称已达到或落后主流多少。
- 未完成同等并发、相同缓存状态下的全矩阵负载测试，不能直接推导主控节省比例。
- 本地存在约 375 KB 的四款 WOFF2 字重，不代表首屏全部下载；未引用的字体文件不算首屏成本。
- Canvas 可能把服务端成本转到客户端；低端手机、触屏精确查看和离屏资源回收必须验证。
- 图表语义对齐比“看起来一样”更重要：现有 stats 的 RRDtool 图形统计与 series 算术统计可能因合并粒度而不同。

## 4. 目标架构和数据规范

### 4.1 保留采集，替换展示路径

```text
SmokePing / 节点上传（不变）
          ↓
         RRD（不变）
          ↓
有限并发的读取层＋有界缓存＋规范统计
          ├─ 轻量批量摘要 → Results、全局坐标范围
          ├─ 有界时间序列 → 可见 Charts → Canvas＋DOM 信息
          └─ RRDtool PNG → 兼容 / 导出 / 显式降级
```

Results 不应为五个统计数字下载每条完整序列；Charts 不应为同一链路重复请求相互矛盾的统计和序列。可在序列响应中附带同一快照摘要，批量摘要与其复用同一规范统计层。

统一 Y 轴根据整个已应用选择集的规范摘要计算，不要求一次下载全矩阵序列。部分摘要未知时显示范围未完整，而非宣称所有图表已严格统一。

### 4.2 数据契约必须先冻结

建议新增版本化契约，例如 `/api/v2/series` 和对应批量摘要；这是待实现设计，不是现有接口。也可以使用明确 schema 版本的兼容扩展，但不得静默更改旧字段含义。

至少规定以下字段和含义：

| 字段类别 | 规定 |
| --- | --- |
| 标识 | source、target、protocol 使用稳定 ID；服务器校验权限边界和链路合法性 |
| 时间 | Unix 秒统一单位；声明请求起止、实际覆盖起止、桶时间代表起点还是终点、实际 step |
| 快照 | generated_at 表示 API 生成时间，不代表测量时间；快照 ID/版本用于响应一致性 |
| 新鲜度 | measurement_updated_at 的可信来源、last_valid_latency_at、age、允许时钟误差；无法可靠得知则 null |
| 摘要 | current/avg/min/max/loss 的明确公式、窗口、样本数、有效覆盖率；数值单位显式给出 |
| 序列 | time、median_ms、必要的 min/max 范围、loss_pct、缺失标记；数组等长、时间有序 |
| 降采样 | 原始/返回点数、算法版本、区间聚合含义；必要时事件聚合数量与范围 |
| 状态 | 传输失败、测量缺失、数据过期、全丢包彼此独立，不挤进一个健康布尔值 |

关键规则：

1. `null` 不等于 0。100% 丢包是一次有效测量，可能没有有效 RTT；完全没有采样不能显示健康或 0% 丢包。
2. Current 对应已定义的最近测量桶。最近测量无有效 RTT 时显示 `—`；若提供“最近有效值”，必须另标时间与历史属性。
3. 新鲜度不能使用请求时间、数组末尾时间或文件 mtime 冒充。P0 核实 `rrdtool lastupdate/info` 与 RRD DS 语义；只有能证明是实际测量更新的值才用于 measurement_updated_at。否则显示“最后已知有效桶”，披露粒度。
4. 现有 20 次 ping、60 秒 step 应从配置核实，不把 `loss × 5` 无解释地固化到公共契约；若做成元数据也不改变采样配置。
5. 将 RTT 中位数时间序列的最值，与单桶内 ping 样本范围分开命名，不混用。
6. 摘要在绘图降采样之前、按统一口径计算；不随画布宽度、DPR、图表库或返回点数改变。
7. 现有 rolling 5 点中位数标准差不是原生网络 jitter。此次不默认展示；若保留 API 字段，标为派生统计并写明公式。
8. RRD 历史合并后不能还原原始 20 个探针的逐次时间信息，不通过插值制造精度。
9. 时间轴明确时区；用 UTC 时间戳传输，界面显示本地时区或明确 `UTC+08:00`，避免含糊的 CST。

### 4.3 降采样与异常保真

- 输出点数同时受窗口实际点数、CSS 宽度和服务端硬上限约束；宽度参数量化为有限档位，防止缓存键无界增长。
- 短窗口且点数不多时不必降采样。长窗口按像素桶保留极值和关键事件，禁止用简单平均抹平尖峰。
- 缺失区间必须断线，不能跨缺口连接；丢包事件与 RTT 空值分别表达。
- “严格点数上限”和“无限多个异常逐点原样保留”不可同时保证。事件过密时按区间聚合并显示数量/最高严重度/覆盖区间，精确数据通过有界明细请求查看。
- Tooltip 不得把聚合桶代表值冒充原始采样；需要显示桶范围或进入明细。
- 用短尖峰、交替缺失、连续全丢包、窗口边缘样本和长时间空档验证，不能只用平滑正常曲线。

## 5. 前端实现原则

### 5.1 请求与状态

- 建立一个统一数据请求调度器，默认最多 4 个在途数据请求；批量摘要也计入。既有服务端限流和 RRDtool 信号量不提高。
- 可见图表优先；请求按链路/窗口/协议/契约版本去重。取消未启动任务，对过期请求使用 AbortController 与 generation 双重保护。
- 503/429 不降级为全卡片散射请求；尊重 Retry-After，有限指数退避加抖动，每轮至多 2 次重试。网络失败不无限重试。
- 只有确认“不支持批量接口”等兼容情形才逐条降级，仍走同一并发队列；部分失败只重试失败子集。
- 缓存采用 TTL＋条目数＋估算字节上限，淘汰使用 LRU；缓存旧值可继续展示，但必须标注过期和最近已知时间。
- 草稿选择、已提交查询、响应快照、图表实例分别管理；旧查询结果不得覆盖新选择。
- 默认保留手动刷新，不偷偷引入常驻轮询。移除无事实依据的 LIVE 脉冲，显示刷新方式、数据时间和异常状态。
- 如后续批准自动刷新：不快于实际采样周期、页面隐藏暂停、请求不重叠，仅刷新当前查询，失败退避。此项独立开关和资源预算。

### 5.2 组件与渲染

- 按状态、API、格式化、卡片、图表、无障碍划分模块；先抽取纯函数和请求层，避免整页一次性重写。
- `Map<stableKey, card>` 管理卡片，避免每个结果扫描所有 DOM。
- 数值差量更新，不为每次数据返回重建整卡片；统一读取布局后再统一写入，去除逐卡 `offsetWidth` 动画重启。
- Canvas 实例仅保留可视区域及有限预加载行，离屏实例销毁或归池；结果数据和用户选择不随视图回收而丢失。
- Results 是否虚拟化由 P0/P4 大列表测量决定。小列表保持简单 DOM，不能为了架构复杂度先加虚拟化。
- 虚拟列表保持滚动锚点、稳定阅读顺序、键盘定位；聚焦项不能在用户操作中突然卸载。
- ResizeObserver 驱动本地尺寸更新；桌面 DPR 上限暂定 2，移动端按清晰度验证 1.5–2，并设置总像素预算，不因高 DPR 无限放大。
- 静止图表无持续 rAF；重绘只由数据、尺寸、坐标或交互变化触发。销毁时移除 observer、监听器、计时器及 canvas 引用。

### 5.3 图表选型与降级

用相同数据、相同尺寸比较现有 PNG、uPlot Canvas 原型；只有原型出现无法合理解决的问题才比较第二个库或局部自绘。

候选必须通过：缺失断线、Loss 标识、统一 Y 轴、触屏和键盘查看、DPR/缩放、生命周期清理、静态自托管、许可证/锁定版本检查。不得引用项目宣传跑分代替本项目实测。

当前 PNG 是中位线/面积加丢包标识，并非完整经典 SmokePing 20 样本烟雾分布；本次必须保留已有信息，但不把“补齐全烟雾分布”设为上线前提。

默认不引入 WebGL、常驻 Worker、自研完整图表引擎或动画库。若实测主线程转换成为瓶颈，再单独论证 Worker 的传输、兼容和维护成本。

降级区分原因：浏览器绘制能力故障可显式改用 PNG；后端繁忙时不能自动让全部 Canvas 又发 PNG 请求。PNG 同样经过有界队列。

## 6. 视觉与交互统一

### 6.1 保留辨识度，消除规则冲突

保留深色工具界面、等宽数值、当前卡片结构、Ext/v4/v6 标签。集中建立颜色、字号、行高、间距、边框、圆角、控件高度、焦点、动效 token；不按卡片数量追加一层覆盖补丁。

每个组件明确默认、hover、focus、selected、disabled、loading、error、stale 状态；选择状态和异常状态不能仅依赖颜色。

- 主数值层级明显但有稳定上限，避免宽屏突然放大到 50 多像素、窄屏又大幅缩小。
- 长节点名优先换行或有可聚焦的完整名称入口；不以无限缩小字号装进卡片。
- 统一路由方向、数值对齐、标签位置；响应式减少列数，不改变指标的阅读顺序和含义。
- Results 隐藏仅 Charts 适用的统一 Y 轴控件；提交按钮文案准确反映当前草稿模式，并提示尚未应用的修改。
- 使用真实数据状态替代装饰性健康灯；刷新失败时保留可辨识的旧值，而不是清空全部内容或假装刷新成功。

### 6.2 可访问性底线

- 按 WCAG 2.2 AA 对相关条款验收；正常文本对比度至少 4.5:1，符合定义的大文本至少 3:1，必要控件边界和焦点状态另行测试。
- 关键数字/正文原则上不低于 14 px，图表刻度与协议标签不低于 12 px。字号是项目设计门槛，不冒充 WCAG 的统一像素要求。
- WCAG 2.2 最小目标尺寸的 24 CSS px 及例外与本项目移动端推荐 40–44 px 区分；不错误认定所有现有 30 px 按钮都违反标准。
- 协议切换使用合适的 `aria-pressed` 或单选语义；拆开节点勾选和 Fix 操作，避免嵌套交互与键盘事件误触。
- 移动抽屉关闭后不可继续 Tab 进入；按实际模态性设置 inert/焦点约束，Escape 关闭并将焦点还给触发按钮。
- 支持 reduced-motion；数字更新和状态灯无无限动画。200% 缩放、320 CSS px 窄屏检查不能遗漏。
- Canvas 提供可读取摘要、单位、时间、缺失说明及按需明细表。Tooltip 不能是精确信息的唯一入口，也不能要求只用鼠标悬停。

## 7. 性能预算与测量方法

### 7.1 预算的性质

下面是待 P0 固化的项目预算，不是已经达成的结果。如需调整，记录原因和对用户体验的影响，不能实施结束后为过关悄悄放宽。

| 指标 | 拟定门槛 | 测量边界 |
| --- | --- | --- |
| 数据正确性 | 黄金样本全通过；未知/过期不误报正常 | 高于任何速度目标 |
| 首开请求 | 用户未提交查询时不加载全矩阵 stats/series/graph | 排除必要 nodes、静态文件 |
| 数据在途数 | 每个页面最多 4；失败重试不放大请求数 | 数据 API 和 PNG 降级共同计数 |
| 脚本/CSS | 初始 JS gzip 暂定 ≤60 KiB；CSS gzip ≤15 KiB | 图表可延迟加载，但须另计完整 Charts 成本 |
| 字体 | 首屏必要字体传输暂定 ≤200 KiB | 保持文字覆盖与版式，不只统计文件夹大小 |
| 即时反馈 | 筛选/点击本地反馈 p95 ≤100 ms | 与网络等待分开；固定设备与场景 |
| 可见结果 | 参考网络首批可见数据目标 ≤2 s | RTT 150 ms、10 Mbps、固定 CPU 档；冷暖分别记录 |
| Web Vitals | 有现场数据时 p75：LCP ≤2.5 s、INP ≤200 ms、CLS ≤0.1 | 移动/桌面分开；无 RUM 时标“未验证” |
| 图表实例 | 随可见区域＋至多两行预加载增长，不随已浏览总卡片数增长 | 记录 DOM、canvas 数与像素总量 |
| 空闲开销 | 无图表持续 rAF；隐藏页不继续后台预取/轮询 | 时钟等必要行为单独计量 |
| 长期运行 | 30 分钟反复操作后无持续增长；扩展 60 分钟复测 | 多轮稳定点比较，不把 GC 抖动当泄漏 |
| 生产安全 | 既有上传成功率、RRD 新鲜度、API 可用性不出现可归因退化 | 不提高主控既有并发上限 |

浏览器数据缓存可从移动端 4 MiB/桌面 8 MiB 的估算载荷预算起试，并设条目上限；这不是总内存保证，JS 对象、DOM、画布和 GPU/图片内存应分别观察。服务端继续使用现有有界缓存；新契约缓存加入统一总预算，不能每个版本各复制一套无限增长。

Canvas 上线需要证明：在代表性 Charts 场景中，主控 CPU 或用户实际等待有明确改善，且浏览器交互/峰值内存不出现不可接受退化。P0 后确定对比阈值与测量误差；不能仅因某个 JSON 更小就宣布成功。若收益不成立，保留 PNG，同时上线已经独立验证的正确性、请求和样式改进。

### 7.2 基准矩阵

- 数据：少量常用链路、双栈混合、外部节点、全丢包、陈旧数据；Results 取接近实际支持上限的矩阵，Charts 对完整支持规模进行滚动，而不是只测首屏。
- 窗口：1/3/6/24h；相同冻结 RRD 副本和固定起止时间，避免前后比较恰好数据变化。
- 视口：390/768/1024/1440/1800 px；DPR 1/1.5/2；另测 320 px 和 200% 缩放。
- 设备：记录真实硬件、系统、浏览器版本；至少 Chromium 桌面和真实手机，再核验 Firefox、Safari/WebKit。CPU 降速模拟不能替代真实手机。
- 场景：首开、提交查询、快速连续切换、滚动到底再返回、统一轴切换、窗口缩放、后台恢复、断网、503、部分失败。
- 缓存：浏览器冷/暖、应用冷/暖、CDN 命中分别标记；生产不清全站缓存制造冷启动，不做高强度压测。
- 重复：关键实验至少 30 次，报告中位数、p95、范围和条件。样本有限时不得宣称具有稳定人口分位代表性。
- 服务器：隔离环境记录每场景 CPU 时间、RSS、RRDtool 调用数、队列等待、响应大小和错误数；生产仅低频只读观察与发布核验。
- 客户端：真实压缩传输字节、首批可见时间、长任务、布局次数、交互、DOM/canvas 数、峰值及稳定内存。

Lighthouse 可以做实验室诊断，TBT 不等于现场 INP。没有合规、低开销的现场数据采集时，不增加第三方分析平台来凑报告；明确报告缺口即可。

## 8. 分阶段执行与验收闸门

每阶段单独提交、单独验证。代码开发授权不等于生产发布授权；实际发布按明确批准的范围执行。

### P0：冻结需求、基线与测试数据

交付：需求矩阵、版本/配置/资源清单、截图、HAR/性能记录、脱敏 RRD 测试样本、统计公式说明。

工作：复核代码与线上一致性；清点实际入口和旧实验代码；确认 nodes 上限、pair 上限、探针种类、DS、step、保留区间及最新更新时间来源；建立前述基准矩阵。脱敏 fixtures 不含登录信息、上传密钥或真实部署凭据。

闸门 G0：现有功能可复现；需求冲突已解决；测试样本覆盖空值、全丢包、过期和极值；性能预算正式记录。不能确认统计含义时，暂停图表迁移但可推进独立的无障碍修复。

### P1：正确性与请求治理（优先级最高）

交付：有界调度器、可靠状态、缓存时效、竞态保护及新增回归测试。

工作：修复批量失败散射、Current 回退、未知 loss、过期缓存静默显示；规范传输状态与测量状态；消除伪 LIVE；补齐按协议和外部标签的测试。

闸门 G1：503/断网测试不产生请求风暴；连续切换无旧结果覆盖；缺测与全丢包可区分；现有后端测试全部通过（基线曾为 33 项，实际以当前发现结果为准）。可以独立发布，不必等待 Canvas。

### P2：组件、样式与发布资源治理

交付：模块边界、token、统一组件状态、键盘/抽屉修复、内容指纹静态资源方案。

工作：保留整体结构渐进抽取；卡片 Map、差量更新、消除逐卡强制布局；合并 CSS 重复规则；修正对比度、标签、字号和响应式；审查字体实际加载。开发构建工具仅用于开发/构建，不在生产新增 Node 常驻服务。

闸门 G2：功能矩阵不回退；各断点截图通过；键盘、触屏、缩放通过；旧 HTML 能取到旧资源，新 HTML 能稳定取得新资源；没有引入未使用的重型运行时依赖。

### P3：规范数据 API 与 Canvas 单链路试点

交付：版本化契约、规范统计纯函数、序列边界、uPlot 原型、PNG 对照报告、渲染器开关。

工作：先实现并测试数据契约，再接单链路 Canvas；复用摘要；加断点/极值/丢包保真；处理尺寸、精确查看、DOM 摘要和可访问明细。

闸门 G3：固定样本数值逐项一致或差异有明确公式解释；Canvas 无伪造点；相比 PNG 有可验证净收益；弱设备通过；PNG 回退可用。失败则调整原型，不继续扩大迁移。

### P4：扩展至完整 Charts、按需渲染与资源上限

交付：视口实例管理、有限预加载、缓存淘汰、必要时 Results 虚拟化、长时间运行报告。

工作：支持全部合法结果、统一轴、长列表、滚动锚点和保留焦点；验证图表不会随浏览数量积累；取消隐藏页无用工作。先设硬边界，再做细微优化。

闸门 G4：最大支持规模下功能完整；滚动不会改变统一轴含义；实例/内存可回收；30/60 分钟测试无持续增长；前端流量没有突破主控承载预算。

### P5：灰度、生产核验与整理

交付：发布包与校验和、测试报告、回滚说明、更新的架构/运维/轻量化文档。

工作：先本地/隔离环境，再使用明确的试用开关让维护者验证；若暂无按比例分流基础设施，不虚构“5% 灰度”。受控试用后再切默认渲染器，观察至少 24 小时，条件允许扩展到 48 小时。

闸门 G5：错误率、上传、RRD 时效与前端反馈无可归因退化；公开地址资源版本正确；新旧客户端兼容通过；回滚演练成功。清理旧代码最后进行，保留 PNG 兼容功能。

阶段依赖：P0 → P1；P2 可在 G0 后并行开发，但独立验证；P3 依赖 G0/G1；P4 依赖 G3；P5 依赖全部相关闸门。工作量主要在数据契约、视觉回归与长列表验证，不能仅按“换图表库”估算；G0 后再给出基于实际差异的工期，不在未完成基准前承诺完成日期。

## 9. 测试与发布保护

### 9.1 必须增加的测试

- 后端单元：统计字段含义、单位、空值、100% 丢包、时钟偏移、窗口边界、粗粒度 RRD、版本兼容、非法链路、参数上限、缓存和并发边界。
- 前端单元：合法配对、标签、排序、格式化、缓存 TTL、请求去重/取消、重试上限、状态代次、降采样极值/断点保留。
- 浏览器 E2E：R01–R12，鼠标/键盘/触屏，草稿未应用，快速切换，离线恢复，滚动复用，抽屉焦点，尺寸变化，旧标签页跨发布。
- 视觉：代表性断点与 DPR、长名称、三位/四位 RTT、0%/100% loss、未知/过期/错误、reduced-motion。
- 性能：固定数据和网络条件下的新旧对比；公开 CDN 压缩与缓存单独验证；重载和恢复不会形成尖峰。

继续使用现有 Python 单测和语法检查。前端 build/unit/e2e 等命令在 P0/P2 新建并记录，不把历史稿中的 npm 命令误认为当前已经可运行。所有生产依赖锁定版本、检查许可证，开发测试依赖不得进入运行包。

### 9.2 发布与回滚顺序

1. 记录已部署文件校验和、API 版本、配置与安全回滚位置；不复制节点登录秘密进仓库或测试包。
2. 先部署兼容 API 扩展，旧页面继续可用；仅按需要重启 API，不重启整个采样/节点体系。
3. 上传带内容 hash 的资源并确认可访问，再原子切换 HTML/资源清单。HTML 重验证，指纹静态资源长期缓存。
4. 小范围启用 Canvas，校验状态、样本和性能；再切默认。开关只控制渲染方式，不作为权限或安全边界。
5. 旧资源保留至少覆盖观察到的 4 小时缓存期与回滚窗口，建议 7 天；API 兼容期限还需考虑长时间打开的旧标签页，不能仅按 CDN TTL 删除。
6. 出问题先切回 PNG/旧前端；新增 API 暂时保留兼容，避免回滚前端反而打不开。涉及后端统计变更时按配套版本回滚，但不回退采样数据。

触发回滚/停止扩大的条件：统计错误、未知误报正常、协议/外部标签错配、核心流程失效、请求放大、持续内存增长、API/上传或 RRD 新鲜度可归因退化。普通网络波动先区分关联性，但数据正确性问题立即停止扩大发布。

生产目录当前不是 Git 工作树：上线必须通过明确的制品/文件映射和校验，不在 `/opt/ipppping` 盲目执行 git pull。代码提交与部署分开记录；获准实施后按项目既有流程同步远程仓库，并以公开站点核验结果证明发布完成。

## 10. 风险登记

| 风险 | 预防措施 | 失败出口 |
| --- | --- | --- |
| RRDtool 与新统计数值不同 | 黄金样本、固定窗口、明确合并和加权语义 | 保留旧 API，暂停新摘要 |
| Canvas 降低服务端成本但拖慢手机 | 真实手机、点数/像素上限、按需实例 | 回到 PNG 或减小绘制工作集 |
| 降采样掩盖异常 | 极值/缺口/丢包专项测试，聚合标记和明细 | 返回更高分辨率但仍有硬上限 |
| CDN 导致新旧代码混用 | 内容指纹、兼容 API、HTML 重验证 | 切回旧清单且保留旧资源 |
| CSS 清理改变布局 | 分组件提交、截图、人工看长文本 | 回退该组件而非整页重写 |
| 虚拟化损害键盘和读屏 | 保持焦点项、稳定 key、替代明细访问 | 小列表关闭虚拟化，调整策略 |
| 失败自动降级引起更高负载 | PNG/JSON 共用队列，503 不散射 | 暂停请求并显示重试入口 |
| 范围膨胀 | 以 R01–R12 为验收边界 | 新主题/Inspector 等另立需求 |

## 12. 外部依据

以下用于选择验收方法，而不是代替本项目实测；核对日期为 2026-09-22。

1. [Web Vitals 官方说明](https://web.dev/articles/vitals)：LCP/INP/CLS 的良好阈值和第 75 百分位要求。实验室数据与现场指标应区分。
2. [WCAG 2.2](https://www.w3.org/TR/WCAG22/)：对比度、键盘、焦点、重排、目标尺寸等验收依据。
3. [文字对比度说明](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum)：普通文字和大文字的阈值不同，不能将装饰色或禁用控件规则套到重要读数。
4. [最小目标尺寸说明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)：24 CSS px 标准及适用例外；项目移动端可另定更舒适的预算。
5. [uPlot 官方仓库](https://github.com/leeoniya/uPlot)：轻量时间序列 Canvas 候选；实施时固定版本并验证功能与许可证。
6. [Chart.js 官方性能指南](https://www.chartjs.org/docs/latest/general/performance.html)：预处理、降采样、关闭不必要动画等通用思路；不意味着本项目要引入 Chart.js。

本计划建议批准的实施边界是 P0–P4 的渐进升级；生产切换依 G5 的验收与明确发布安排执行。若只希望先批准最小风险部分，可先完成 P0/P1，得到可独立上线的正确性与请求治理改进，再决定 Canvas 迁移。
